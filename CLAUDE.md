README.md covers quickstart, CLI, protocol, and env vars — don't duplicate those here; the slice ledger below is the one status summary kept in this file. ## Architecture — the invariants that span packages

Dependency direction: `core ← runtime ← tools, mcp, gateway ← cli`. `packages/runtime/src/types.ts` is the cross-package contract (`Provider`, `Tool`/`ToolContext`, `Messenger`, `AgentLoopOptions`, `ToolCatalogView`/`DeferredTools`); change it deliberately. `@pinky/mcp` imports core + runtime and is imported only by cli — core may not import runtime, which is why `CatalogHit`/`CatalogEntry` are declared in BOTH `core/tool-catalog.ts` and `runtime/types.ts` and satisfied structurally; keep the two in step.

**1. The event log is the state; the prompt is a projection.** Every thread `(tenantId, channelId, threadId)` is an append-only `events` row sequence (`seq` per thread, assigned under a `threads` row lock). `runAgentLoop` (runtime/loop.ts) loads `EventStore.contextEvents()` — events from the latest `continuity` event onward, newest-kept if over the cap — and `buildContext()` (core/projection.ts) renders only `ingress`/`a2a`/`notice`/`message`/`tool_result`/`continuity` **plus the `block` of the FIRST `memory` recall event in the window carrying the `block` KEY** (hoisted to index 0 ahead of the continuity doc, and only when non-empty — DESIGN §3); everything else (`decision`, `egress`, `error`, `restart`, `config`, every other `memory` event) is audit-only. `memory` is no longer blanket audit-only: that one `block` is the exception, and it exists so a wake replays the injected text instead of re-searching for it. **Tool-call args are canonicalized at BOTH ends** — `canonicalizeArgs` (core/events.ts; recursive key sort by code unit, arrays untouched) is applied once per turn in the loop (`canonicalizeTurn`: the journaled `message` event, the in-run assistant message, and the calls it executes) and again by the projection on the way out — because jsonb re-sorts an object's keys by (length, bytes), so a replayed `tool_use` would otherwise differ byte-wise from what the run sent: one cold prefix per wake (§4.5). It is a cache-alignment invariant, not a formatting nicety. Never mutate stored events; append. `seq` is `bigint` and postgres.js returns it as a string — coerce with `toSeq()` at the store boundary, never compare raw.

**2. Context restarts, not compaction (DESIGN §4).** `ShedContextTool` (runtime/continuity.ts, deliberately *not* in `createTools()`) validates a `ContinuityDoc` and emits a `continuity` event; the loop then rebuilds messages from the new boundary and continues. The pressure ladder in loop.ts injects `[harness notice]` messages as **user** role — never `role: "system"` mid-conversation and never by rewriting `opts.systemPrompt` — because the system prompt is the cached prefix (§4.5/§9); each notice is **journaled as a `notice` event immediately before it is pushed**, so the successor wake's projection reproduces it in the same slot and the transcript stays a prefix-extension. The advisory notice is armed **from the log** (`advisoryArmed = !windowHasAdvisory(events)`), so it fires once per WINDOW — a shed re-arms it — not once per wake; the hard and retry notes are per forced TURN, so a model that refuses to shed accumulates two more of them per wake. The hard rung fires on the token fraction **or on a truncated context window** (`ContextWindow.truncated`): the cap keeps the newest events, so a truncated window's start rolls forward with every append and can never cache-hit — a shed is the fix, and the rung re-arms off the rebuilt window. The forced turn never narrows the `tools` array (that invalidates every cache tier) and is **two-step**: the FIRST attempt sends the full tool list, `HARD_NOTE`, and **no `tool_choice`** — an appended notice extends the prefix and stays warm, and the note plus the harness guard (which errors every non-shed call) are what hold the boundary; only the RETRY (`forcedShedFailures > 0`) adds `toolChoice {type:"tool", name:"shed_context"}`, because `tool_choice` invalidates the whole messages tier — one uncached re-read of the transcript at exactly its largest — and that guarantee is only worth paying for once an attempt has failed. `HARD_NOTE` still tells the model shed_context is "the only tool available this turn"; the guard is what makes that true. The projection drops `tool_result`s whose call isn't rendered (a shed leaves one orphan by construction). Every rebuild journals an audit-only `restart` event (`boundarySeq`, `tokensBefore` → `tokensAfter`, `recallTokens`, `messages`) — once per boundary: by the loop right after a shed, or backfilled on the successor wake when the shedding run stopped first. `pinky stats restarts` joins it to the next `message`'s `usage` (the cache-write-heavy first turn) and is **half** the DESIGN §13 cost query; `pinky stats cache` is the other half — the steady-state hit share across every turn with `usage`, on **one denominator**: the turns with a computable hit share (`with cache counters N`) carry the mean and every token total (`tokens over the N measured turns …`). `⊘ cold` is **read-counter-only** (the previous turn in the same thread read ≥1024 and this one read 0 on a prompt >1024), so it fires on OpenAI/DeepSeek too; "prefix rewritten" is **write-counter-only** and prints `n/a (no turn reported a cache-write counter)` where nobody counted. `--limit` samples the newest N turns and transitions are detected inside that sample, so a thread's first sampled turn is never cold. Neither is model-visible.

**3. Two config layers; one human write path, one gated agent write path (P8, revised).** `loadEnvConfig()` = bootstrap only (DB URLs, secrets, node id, port). Everything behavioral (`model`, context thresholds, `memory.*`, `selfConfig.*`, `tenantId`) is the `settings` table, read via `SettingsStore.load({ scopes })` with overlay `global < channel:<id> < agent:<id>` and run through `validateSettings()`. Long-lived surfaces reload per run with `["channel:<thread.channelId>", "agent:<id>"]` (`makeRunAgent`'s `settingsFor`), which is what makes a write visible on the *next* run. **Config never lives in a file** — that is the point: a bad value can't stop a boot. The human CLI (`pinky config set`) is the default write path. The *only* agent write path is the `settings_set` tool (tools/settings.ts): gated on `selfConfig.enabled` + `selfConfig.allowedKeys`, scoped to `agent:<self>` or `channel:<current>` (never `global`), with `tenantId` and `selfConfig.*` hard-denied even by `"*"`, validated by `SettingsStore.set` **before** the insert (a bad value is a tool error, never a broken table), and journaled as an audit-only `config` event. Don't add a second agent write path, and never a file-based one.

**4. Db contract (core/pg.ts header).** Positional `$n` params. **jsonb params take plain values — never `JSON.stringify` them** (postgres.js serializes once; double encoding stores a jsonb *string*; `0004_jsonb_repair.rerun.sql` exists to undo exactly that). Bare booleans/Dates/bigints go through `jsonbParam()`. `withTenant(db, tenantId)` wraps a `Db` so every tx opens with `set_config('pinky.tenant_id', …, true)` — that GUC is what the `memories` RLS policy keys on; RLS only bites under the `pinky_app` role (superuser bypasses). Migrations: `NNNN_name.sql` runs once and is recorded (unguarded DDL — it must fail loudly, not record itself as applied); `NNNN_name.rerun.sql` runs on every migrate, must be idempotent, and DO-block-guards `insufficient_privilege` because `memory`/`smoke`/`prompt`/`headless` auto-migrate at startup via `bootstrap()` (`config` does not).

**5. Headless JSONL pipeline (gateway/headless.ts, DESIGN §11 gateways).** Slack is gone; the primary ingress is a stdio protocol: one command object per stdin line, one event object per stdout line. `parseCommand` (a rejection is a value, not a throw) → `EventSink.ingest(thread, externalId, [ingress])` writes the dedup claim + the `ingress` in **one transaction** (`null` return = already seen ⇒ no run) → enqueue on a per-`(channelId, threadId)` promise chain → **one** `runAgent(thread, batch, hooks)` per prompt, serialized per lane, concurrent across lanes. The loop streams every event it appends through `AgentLoopOptions.onEvent` (fire-and-forget; a throwing observer can't kill a journaled run) and every `deliver()` becomes a `reply` line. Ordering is guaranteed **per thread**: `run_started → (event | reply)* → run_finished`; a thrown run gets `error` instead of `run_finished`. Every prompt is addressed to the agent, so there is no reply gate on this path. **stdout is protocol-only** — `opts.write` is the single output path, everything human goes to stderr (that includes Postgres notices, `core/pg.ts` `onnotice` → `console.warn`). `gateway/server.ts` is now A2A relay only (`GET /healthz`, `POST /a2a/deliver`), started only by `pinky headless --a2a`.

**6. A2A (DESIGN §7).** Addresses are `agentId@nodeId`; `Mailbox` is bound to its node and normalizes unqualified / `@<self>` addresses to itself. `LocalMessenger.send()` persists first (at-least-once), then fires local subscribers or POSTs an HMAC-signed envelope to a peer. **Idempotency hinges on the delivery claim, not row existence**: `receive()` = insert-if-absent, then `claimDelivery()` (`update … where delivered_at is null returning id`), firing only on a successful claim — this is what makes separate-DB nodes, shared-DB nodes, and replays one code path. `flushPending()` re-sends undelivered rows (re-stamping `sentAt` for the 300s freshness window). **Delivery is bookkeeping; consumption is a receipt** (issue #4): `delivered_at` only says this node took custody, so the receipt is `read_at`, stamped by the CONSUMER via `claimConsumption(id, tx)` **inside the same transaction that journals the `a2a` event** — both commit or neither does, and a rolled-back turn is redelivered instead of lost. Recovery is therefore stateless: `redeliverUnconsumed(agentId)` re-fires everything unread (whatever `delivered_at` says), at startup — `pinky headless`'s `wakes` seam, awaited before the first stdin line — and again on the 30s `startA2ASweep()`, which now runs with or without peers, logging to **stderr**. Re-firing is free because the consumer's claim is the idempotency hinge. The projection renders `a2a` as a `user` turn, so a woken run sees what woke it. **Any future timer/scheduler follows the same shape: it emits an event and the consumer journals the receipt — never mark something 'fired' from the scheduler side.**

**7. Providers (runtime/providers).** `retry.ts` is shared: retries 408/409/429/5xx/network with jittered backoff and `retry-after`, per-attempt timeout, and **never after the stream has yielded**. Model ids are `provider/model-id` (`openrouter/moonshotai/kimi-k2` → OpenAI-compatible route); `splitModel` splits on the first `/`. Caching, which is a prefix match over `tools → system → messages`:
- **Anthropic** puts at most **three** `cache_control` markers on a request (of the 4 allowed): the stable system block (`buildSystemBlocks` — suffix blocks stay unmarked), and the **last content block of each of the last two messages** (`applyMessageCacheBreakpoints`, a rolling window: the older marker is this turn's read point, within the ~20-block lookback; the newer is what the next turn reads). **One TTL for every marker** — mixing requires longer-before-shorter ordering — set by `PINKY_ANTHROPIC_CACHE_TTL` (`5m` default | `1h`, ~2× vs ~1.25× write cost). `cache: false` emits none; `cacheSystem` is a deprecated alias of `cache`. `CompleteOptions.cacheKey` is **ignored** here (Anthropic keys on prefix bytes).
- **`toolChoice`** maps to `tool_choice` on both routes — `auto` / `none` / by name (Anthropic `{type:"tool",name}`, OpenAI `{type:"function",function:{name}}`) — sent **only when `tools` is non-empty** (the API rejects the pairing otherwise) and omitted entirely when the caller sets nothing, so an unmasked request is byte-identical to what it sent before this existed.
- **OpenAI/DeepSeek/OpenRouter** cache automatically; there is nothing to mark. Their `prompt_tokens` **includes** cached tokens, so `toTokenUsage` subtracts `prompt_tokens_details.cached_tokens` / `prompt_cache_hit_tokens` (and OpenRouter's `cache_write_tokens`) out of `input` to keep the `TokenUsage` convention true: `input` is the **disjoint uncached remainder**, prompt = `input + cacheRead + cacheCreation`. A route that counted nothing leaves the fields **absent**, never `0` — "nothing cached" ≠ "nobody counted". `cacheKey` (the loop's `tenant/channel/thread`) ships as `prompt_cache_key`, a shard-routing hint — but it is an OpenAI-**native** body field, so the default is route-dependent: `createProvider` turns it **on only for `openai/` against real api.openai.com** (no `OPENAI_BASE_URL`) and **off** for `openrouter/` and for any `openai/` pointed at a base-URL override (vLLM, llama.cpp, LM Studio, Azure — strict servers 400 an unknown top-level field). `PINKY_LLM_PROMPT_CACHE_KEY` wins on every route; a non-boolean throws at construction.

**8. Tools: the header/catalog partition (packages/tools, runtime/deferred.ts — slice 9).** Tool schemas render at prefix position 0 (`tools → system → messages`), so the tool list is the head of the cache key and **loading a tool never rewrites the header — a loaded schema is APPENDED as an ordinary `tool_result`**. The header holds the always-on tools plus three meta-tools (`tool_search`/`tool_describe`/`tool_call`, tools/src/deferred.ts, **registered unconditionally** in `createTools()` so their presence can never flip with whether a server was up); everything else lives in the catalog. `partitionTools(tools, settings.tools, sourceOf)` (pure, runtime/deferred.ts) splits by `alwaysOn > deferred > defaultMode[source]`, with `META_TOOL_NAMES` + `shed_context` pinned to head and both halves sorted by **code unit** — that order is a cache key, so never re-sort downstream. `sourceOf` is structural: `name.startsWith("mcp__") ? "mcp" : "builtin"`. The partition happens **per run in `makeRunAgent`** off the RELOADED settings (`builtins + boot.mcp.tools()`), `head` becomes both `AgentLoopOptions.tools` and the input to `buildSystemPrompt` — which is therefore memoized on `name\0firstLine(description)` per head tool, not built once per process, because `alwaysOn` can change between wakes. **`alwaysOn` change = header change = full cache invalidation; `deferred` change is free.** Within a run the set is still fixed: masking is `tool_choice` only, never a shorter array. The deferred half becomes a `DeferredToolRegistry({ catalog, tools, headNames })`; `validateArgs` does a deliberately small JSON-Schema check (required keys, top-level types/enums, `additionalProperties:false` honoring `patternProperties`) and a failure returns the **full schema inline** so the model self-corrects without a describe round-trip. `tool_call`'s three refusals are distinct on purpose: a **head** tool ("already in your tool list, call it directly"), a built-in from **another surface** ("not available here" — `upsertBuiltins` never withdraws, so the catalog is tenant-wide), and an MCP tool whose **server is offline** (retryable). `shed_context` stays out of `createTools()` and is appended by each surface. Path tools go through `sandboxResolve` (lexical containment under `ctx.cwd`). `bash` is unchanged: excluded from `createTools()` unless `{ shell: true }` — `pinky prompt` opts in, `pinky headless` only with `--shell`. `recall`/`retain`/`memory_edit`, `settings_get`/`settings_set` and the three meta-tools all degrade to a clean `isError` when the runtime hands them no `ctx.memory` / `ctx.settings` / `ctx.deferred`. `ContinuityDoc.workingSet.tools` carries deferred tool names across a restart (`- tool: <name>` in `serializeContinuity`), so the successor describes instead of re-searching.

**9. Memory plane (packages/core/src/memory.ts, DESIGN §5).** `new MemoryStore(db, tenantId)` takes the **withTenant-wrapped** db *and* the tenantId: RLS keys on the `pinky.tenant_id` GUC but is bypassed by a superuser (which a dev checkout is), so the store also writes `tenant_id` and repeats it in every WHERE. Every read goes through `scopePredicate()` (§5.1) — never a filter applied afterwards. **Invalidate, never delete**: nothing here issues a DELETE; `update()` stamps `valid_to` and inserts the replacement in one transaction. Retrieval is two voices (pgvector cosine + Postgres FTS on the generated `tsv`) fused by `fuseHits()` (RRF k=60, then recency/importance rescore); either voice may be absent and both absent degrades to a newest-first listing. **Vector params are the pgvector text form** `'[0.1,0.2]'` (`vectorLiteral()`) with an explicit `::vector` cast — a JS `number[]` binds a `float8[]` postgres refuses to coerce. Embeddings are optional *everywhere*: `supportsVectors()` (one cached probe for `memories.embedding`) gates both the embedding on `retain` and the vector voice on `search`, and a missing API key means `createEmbedder` throws an `embeddings disabled:` error the caller catches, warns once, and runs FTS-only — so build every embedder/embedding field with a conditional spread. Auto-recall (`runtime/memory-recall.ts`) injects the `<memories>` block as a **`user` message at index 0**, budgeted by `memory.recallTokenBudget` — never the system prompt (§4.5/§9 cache prefix). It runs **once per WINDOW, not once per wake**, gated on a `memory` recall event carrying the `block` **KEY** — `windowRecall(events)` (core/projection.ts) → `{ ran, block, scope? } | null`. Present-and-empty (`""`) claims the window too: a pass that found nothing has to close the gate, or one later `retain` would unshift a block at index 0 on the next wake and cold-start the whole prefix. The projection hoists only a NON-empty block. Agent-initiated `recall` tool calls journal **no** key and can never claim a window, so nothing the agent does mid-window rewrites byte 0; a store failure journals nothing at all and the next wake retries — the one place eventual recall beats prefix stability. The event also carries `scope: { includeUser, includePrivate }`, because the block is REPLAYED: a later wake replays it only while that run's memory settings are on (`opts.memory` present and `memory.autoRecall` true — otherwise the projection's hoist is stripped) and its scope is not NARROWER than the journaled one. A narrower run strips it and re-recalls under its own scope, journaling a second, narrower event (the projection keeps hoisting the FIRST, so that costs one prefix break per narrow wake — §5.1 privacy wins); a wider scope replays as-is. A fresh boundary has no block, which is what keeps "at context start and after each restart" true. `config` events and every non-window-opening `memory` event stay audit-only.

**10. MCP plane (packages/mcp, DESIGN §7.1).** One `McpManager` owns every configured server. **Naming is `mcp__<server>__<raw>`** — server key validated `^[a-z0-9][a-z0-9_-]{0,31}$` **with `__` banned** (it is the separator, so `github__issues`+`create` and `github`+`issues__create` would collide on one `tool_catalog` primary key), raw sanitized to `[A-Za-z0-9_-]`, total capped at 64 with an 8-hex sha256(`server\0raw`) suffix on truncation *and* on a sanitization collision (the loser is disambiguated, never dropped). `callTool` must send the server's **raw** name — the authority is the catalog's `raw_name`, never `splitMcpToolName` (sanitizing is lossy). **`versionNegotiation: { mode: "auto" }` is mandatory** — the SDK default is `legacy`, which talks to a 2026-07-28 server as if it were 2025 and hides ttl hints and `subscriptions/listen`; both eras are live (modern probes `server/discover`, legacy falls back to `initialize` + unsolicited `notifications/tools/list_changed`). **`start()` never blocks on a server**: it awaits one `serverState()` probe each and connects on background loops. A matching `configHash` (sha256 of canonical JSON with `${ENV}` placeholders **unresolved**) makes the catalog trusted, and the generation is rebuilt from `catalog.entries()` — not `describe()` — so `tools()` is complete *before* the connect and the header is byte-identical across it. **Schema keys are canonicalized on BOTH paths** (`sortObjectKeysDeep`): jsonb re-sorts object keys, a live `tools/list` does not, so without it the cache path and the sync path send different bytes at position 0. A sync is one `replaceServer` (upsert + `removed_at`, one tx); **a disconnect writes nothing** (an outage must not flap the list) and a **failed catalog write never drops the connection** (that turns one oversized description into an endless respawn loop) — it keeps the generation and retries with full-jitter backoff. Caps, all load-bearing: description 8000 chars and schema >64 KB stubbed (a tsvector is capped at 1 MB and one oversized row aborts the whole generation), result 50 KB (render.ts, same as `bash`), ttl refresh clamped to 60s–24h (`setTimeout` overflows past 2^31 and fires immediately). `redirect: "error"` whenever an http server has custom headers, because `fetch` replays them across origins. **No roots / sampling / logging / elicitation** (all deprecated in 2026-07-28): a `resultType: "input_required"` result is a clean tool error. `close()` closes subscriptions → clients → transports, which is what **reaps the stdio children**, and the CLI's `installShutdown` wires SIGTERM/SIGINT to drain → `boot.close()` (MCP before the pool) → exit 143/130, with a second signal and a 10s grace as valves. **Every line goes to the injected `log`, i.e. stderr** — stdout is the JSONL protocol. `mcp.servers` is read ONCE at bootstrap from global + agent scopes (a channel-scoped row is ignored and warned about) and is **immutable to `settings_set` even under `"*"`**: a stdio `command` is arbitrary host execution.

**Prompt-cache discipline (cross-cutting; §4.5/§9).** The cached prefix is `tools → system → messages`, matched byte-for-byte from position 0, and a break costs the whole thread, so: never change the **tool list** or the **model** mid-window (mask with `tool_choice`); **loading a tool APPENDS a result, it never rewrites the header** — that is the whole point of the catalog, and the header only moves when a human or an allow-listed agent changes `tools.alwaysOn` (#8) or an MCP schema genuinely changed; never put volatile content in the **system prompt** (no timestamps, no per-turn counters — it is the cached head, and a mid-conversation `role:"system"` message is folded into the system field by the Anthropic route, shifting every byte of the conversation behind it); anything the loop pushes into `messages` must be **journaled first**, so the projection reproduces it and wake N+1 is a byte-extension of wake N (that is why `notice` events and the recall `block` exist); what the log hands back must render the **same bytes it went in as** (canonical tool args, #1); append at the tail, never edit or re-render an earlier message. Verify with `pinky stats cache` — a `⊘ cold` transition or a "prefix rewritten" turn means one of these rules broke, and it is a bug in request assembly, not a property of the workload.

## Testing conventions

- Unit tests use hand-rolled fakes: a `FakeDb` that records SQL/params (assert on SQL fragments and `params`, and on `txLog` for "one transaction" claims) and `FakeProvider` (scripted `AssistantTurn[]` or a function). Snapshot prompts passed to the provider — the loop mutates the array it hands over.
- Integration tests live in `packages/{core,runtime,cli}/test/integration/`, gated on `process.env.PINKY_INTEGRATION === "1"`, read the DB URL from `loadEnvConfig()` (CI uses port 5432, local 5544), use unique ids per run, and delete only what they created. Tests named `DEFECT: …` are regression guards for bugs the unit suite missed — the SQL is only exercised here, so a green `bun test` is not evidence for anything that touches Postgres or the wire.
- `cli/test/integration/headless.test.ts` spawns `pinky headless` as a **real child process** with the channel's model set to `fake/echo`, and asserts every stdout line parses as JSON. It is the only test that can catch something on the startup path printing to stdout; `gateway/test/headless.test.ts` injects `write`, so a stray `console.log` is structurally invisible there.
- The vector voice runs only where pgvector exists: CI (`.github/workflows/ci.yml`, `pgvector/pgvector:pg16`) and locally on 5545 via `db:up:vector` + `test:integration:vector`. On the default alpine server `memories.embedding` never exists, so `supportsVectors()` is false and the FTS-only branch is what gets executed — both branches matter, run both.
- Integration assertions must not depend on server collation: the pgvector image is Debian/glibc `en_US` (hyphens ignored at the first level), alpine is C, so `order by <text>` disagrees with JS `.sort()` for some random run ids. Sort on the JS side of every comparison (a real CI flake, fixed in `da33d0e`).
- `runtime/test/providers-caching.test.ts` is the cache-layout suite: it asserts the exact bytes each route posts (marker placement, TTL, `tool_choice`, `prompt_cache_key`, the usage mapping) and the env parsers behind them. Any change to request assembly belongs there. `runtime/test/integration/providers-cache.test.ts` is the only proof a cache *hit* happens — gated on `PINKY_INTEGRATION=1` **and** `ANTHROPIC_API_KEY` (missing key = clean skip). It is not free: two calls whose system prompt is padded to ≈13–15k tokens (Haiku's minimum cacheable prefix is 4096, and a shorter one simply never caches), **~$0.02 per run** even at `max_tokens: 16`; model overridable with `PINKY_CACHE_TEST_MODEL`.
- `runtime/test/loop.test.ts`'s `FakeDb` has two seams. `seed()` lands events directly in the store, bypassing `EventStore.append`: the only practical way to observe a window past `DEFAULT_CONTEXT_EVENT_CAP` (5000) and therefore the truncated-window pressure rung (seq bookkeeping matches `append`'s, so the store keeps working afterwards). `reorderJson = true` reorders every stored `data` object's keys on READ the way jsonb does — off by default, on for the cache-alignment tests, because a fake store that preserves insertion order makes the whole "wake N+1 renders different bytes" class structurally invisible.
- `bun run smoke` marks each fixed `cli:smoke/*` thread with a per-run **seq** (`latestSeq`, then `history(ref, { afterSeq })`), never `history().length`: `history()` is a forward page capped at 500 rows, so on a long-lived dev DB the mark sticks at 500 and every check reads an empty slice (a red smoke CI's fresh database hid).
- `bun run smoke` also covers the memory plane (retain → recall through the tools, plus auto-recall injecting `<memories>` at `messages[0]` on a fresh thread) with a `FakeEmbedder` at 1536 dimensions so it matches the real column in CI — and, since slice 9, a fourth leg that spawns the modern MCP fixture as a REAL child, syncs the catalog, runs `fake/deferred` through `tool_search → tool_describe → tool_call`, asserts the header held (three meta-tools in, zero `mcp__`), deletes its own `tool_catalog` rows, and checks the child was reaped.
- `packages/mcp/test/` has two fixtures because the fallback cannot be faked: `modern-server.ts` is built with `@modelcontextprotocol/server` (a **devDependency of the root package.json, fixtures only**) and answers `server/discover`, so it negotiates 2026-07-28; `legacy-server.ts` is ~60 hand-rolled lines that answer `server/discover` with -32601, which is the only way to make the SDK take the 2025 `initialize` path (an SDK-built server would answer the probe). `mcp-stdio.test.ts` drives both over real stdio, and its `DEFECT:` test spins up **two managers over the same fixture** — one served from the catalog, one from a live sync — and asserts byte-identical schemas: that is the guard on the header staying stable across a restart. The unit suite uses `InMemoryTransport` and a fake catalog, which proves message handling and nothing about spawning.
- `fake/deferred` (runtime/providers/fake.ts) scripts the four turns of the meta-tool round trip and closes with `FAKE_DEFERRED_MARKER`, so asserting on that marker asserts all four ran — a lucky echo cannot produce it. It searches for whatever `mcp__` tool matches `FAKE_DEFERRED_QUERY`, so it works against any echo-shaped fixture rather than one.

## TypeScript notes

`exactOptionalPropertyTypes` is on: build optional fields with conditional spreads (`...(x ? { x } : {})`), not `x: undefined`. `verbatimModuleSyntax` is on: `import type` for types. The repo has exactly **two** runtime dependencies — `postgres` and `@modelcontextprotocol/client` (2.0, `@pinky/mcp` only; the legacy monolithic `@modelcontextprotocol/sdk@1.x` is NOT what this is) — plus `@modelcontextprotocol/server` as a root **devDependency for the test fixtures only**. Don't add more without a reason; the argument-checking in `runtime/deferred.ts` is deliberately hand-rolled rather than a third.
